# SNX Phase 3A — Partner + Proposal Audit

Date: 2026-09-02
Scope: audit only. No product code was modified in `bcc-website` or `sanctuary-nexus` while writing this document.
Branch context: `bcc-website` is on `preview/phase-2c-products` (see `SNX_OPERATOR_SESSION_HANDOFF.md`). This audit is the pre-work for the "Partner + Proposal" item flagged as **not started** in that handoff's "Next recommended module" section — it does not begin implementation.

## Method

Two mockups were supplied as **design intent**, not implementation truth:

- **Primary reference:** `Partner & proposal workflow.jpeg` — an 8-step flow (Partner → Opportunity/Deal Context → Setup → Hermes Draft → Review → Approve → PDF → Agreement/Next Action).
- **Secondary reference:** `People, Partner, Inquiries.jpeg` — canonical-record architecture (one Person, one Partner, with Bookings/Inquiries/Proposals/Agreements/Communications all linked back to those two canonical records).

The real implementation lives outside this repo, in the separate Living OS codebase at `/Users/guide/Desktop/Ox/sanctuary-nexus` (Next.js 14 app, not deployed, not wired into `/operator` in `bcc-website` in any way today). This audit re-reads the actual source there — `src/lib/partners.ts`, `src/lib/proposals.ts`, `src/lib/proposalDocument.ts`, `src/lib/proposalWritingStandard.ts`, `src/lib/partnershipFramework.ts`, `src/app/api/partners/route.ts`, `src/app/api/proposals/route.ts`, `src/app/api/proposals/[proposalId]/pdf/route.ts`, `src/livingos/components/workspaces/partners/{ProposalBuilder,PartnerActionsPanel}.tsx`, and the Partner Hub detail page — cross-checked against the prior `OX_OPERATOR_REUSE_AUDIT.md` (2026-09-01, also in that repo) rather than trusting that audit's summary alone.

**Critical framing carried over from the prior audit and reconfirmed here:** none of this is a production system. It's a local Next.js app persisting to `.sanctuary/runtime/work-data.json` (a JSON file) with no deployed auth, no durable database, and zero connection to the BCC/BNT Supabase project this repo runs on. "Implemented" below means *implemented and working locally in Living OS*, not *available in `/operator` today*.

## Part 1 — Partner + Proposal Workflow (primary mockup)

| Mockup step | Real implementation | Verdict |
|---|---|---|
| **1. Partner** — directory, search/filter by brand, select or create | `Partner` is a canonical record (`src/lib/partners.ts`) with `displayName`, `legalName`, `aliases`, `organizationType`, `relationshipStatus`, contacts/venues/businessLinks/notes/agreements nested arrays. `resolvePartner()` does real entity resolution (exact + substring match) specifically to prevent a duplicate SOHO from a spelling variant. Partner Hub list + detail pages exist and read/write through `/api/partners`. Inline "create partner" exists inside the Proposal Builder itself. | **Matches.** The mockup's multi-brand filter chips (BEST/BCC/Flow Lab/YTG) don't exist as UI, but the underlying data supports it (`businessLinks[].business` is brand-scoped) — a filter is a small addition, not a missing model. |
| **2. Opportunity / Deal Context** — venture, commercial model, primary objectives | `Proposal.business` / `.product` select the business/product line; `dealVariables` (commission, entry-terms, minimum-spend, guaranteed-traffic, operating-rules, contract-period, exclusivity) carry the commercial model. Values are carried forward from the latest proposal on the same partner+business+product line so terms aren't re-entered. | **Matches**, with a narrower field set than the mockup implies. The mockup's "Primary Objectives" (drive attendance / ticket sales / VIP alignment) and free-text "Estimated Guests" are not modeled — only the 7 fixed deal variables above exist. |
| **3. Proposal Setup** — structured, editable sections (Opening, Collaboration Summary, Structure/Offers, Benefits, Deliverables & Support, Commission, Terms, Next Steps) with a mapped-variable count and per-section edit icons | The real structure comes from `PROPOSAL_WRITING_STANDARD.structure`: *Partnership Opportunity → About Sanctuary Nexus/the business → About the product → Proposed Collaboration → What We Bring → Partner Benefits → Commercial/Partnership Terms → Operating Model → Review & Next Steps*. This is real and versioned (`writingStandardVersion` is stamped on every proposal), and it maps closely onto the mockup's section list conceptually. | **Partially supports.** The mockup shows *per-section structured editing* (click a section, edit its fields, see "12 variables mapped"). The real system does not — it produces one flowing markdown draft from the template + deal variables, editable only as a whole (direct text edit) or via a natural-language "Request Changes" instruction / full regenerate. There is no section-by-section editor, no attachments/photo upload, no explicit "Event Dates" or "Est. Guests" fields. |
| **4. Hermes Draft** — AI generates a first draft using partnership context and deal variables | `generateProposalDraft()` (`src/lib/server/proposalGeneration.ts`) composes Framework + Writing Standard + Product Profile + Partner/Deal Context and calls Hermes when `HERMES_API` is reachable, with a **deterministic fallback** template when it isn't — so a draft is always produced, never blocked on the LLM. `writerMode` (`"ai"` \| `"deterministic"`) is recorded on the proposal. | **Matches**, including the AI-optional design the mockup implies with its "Hermes prepared a draft" framing. This is real, not simulated. |
| **5. Proposal Review** — draft/needs-draft/needs-review states, inline comments & annotations, named reviewer avatars, version label | `ProposalStatus` = `draft \| review \| approved \| exported \| sent \| archived`. Preview/Edit toggle exists. "Request Changes" (targeted AI revision via free-text instruction) and "Regenerate" (fresh draft, same inputs) both exist and are real API actions (`PATCH /api/proposals`). | **Differs.** There is no comment/annotation system anywhere in the code — no inline comments, no per-line markup, no multiple named reviewers, no comment timestamps/avatars. "Review" is a status value with no dedicated screen; the closest real behavior is the single free-text "Request Changes" instruction field. The mockup's collaborative-review surface (Hermes AI + James Parker + Alex K. each commenting) is **mockup-only, not implemented.** |
| **6. Approve** — freezes a version, shows audit trail (created/reviewed/approved with names+timestamps) | `PATCH action=approve` freezes `approvedContent` (immutable from that point), sets `approvedAt`, and blocks the check unless required deal variables are filled (`missingRequiredVariables`, overridable with explicit `allowMissing: true`). Once frozen, any draft-mutating action (`edit`, `regenerate`, `request-changes`, `update-variables`) is rejected with 409 until a new version is branched (`create-version`). | **Matches** on the mechanics (freeze + version branching is real and correctly implemented). **Differs** on presentation: there's no structured audit trail UI showing *who* created/reviewed/approved and *when* per actor — only a single `approvedAt` timestamp on the record. No named-actor log exists (no user/auth model to attribute actions to a specific person at all — see Part 3). |
| **7. PDF** — client-facing document, sent/tracked, "PDF Sent" state | `GET /api/proposals/[id]/pdf` renders the **approved, frozen** content into a real multi-page A4 PDF via `pdfkit` (`src/lib/proposalDocument.ts` + `src/lib/server/proposalPdf.ts`), strips all internal metadata (ids, version headers, status) so the client only sees the clean document, and produces a client-friendly filename (`SOHO-Hospitality-Group_Bangkok-Club-Crawl_Partnership-Proposal.pdf`). Generation is blocked until the proposal is `approved`/`exported`/`sent`. `generate-pdf` sets `finalArtifactRef` and flips status to `exported`. | **Partially supports.** PDF generation itself is real and correctly gated on approval — this is genuinely implemented, not a mockup fabrication. But there is **no "sent" tracking**: nothing marks *when/how* a PDF was actually delivered to the partner, no delivery confirmation, no PDF stored as a durable binary (`OX_OPERATOR_REUSE_AUDIT.md` §4 already notes PDFs are generated on request, not persisted). The `sent` status exists in the type but nothing in the code transitions a proposal into it automatically — it's reachable only via the generic `set-status` action. |
| **8. Agreement / Next Action** — signed agreement, audit trail, "Log Meeting" / "Send follow-up" quick actions | `PartnerAgreement` exists as a metadata record (`relatedProposalId`, `businessesOrProducts`, `venues`, `effectivePeriod`, `commercialTerms`, `specialConditions`, `fileOrLink`, `status: draft\|active\|inactive\|terminated`, `reviewDate`). `POST /api/partners action=add-agreement` can create one. Partner detail page renders an "Agreements" section read-only. `PartnerActionsPanel` supports free-text "Add a relationship note" and "Review date / Next action" fields. | **Differs significantly.** No e-signature capture anywhere (no `signedBy`/`signedAt`, `fileOrLink` is just an optional string). No agreement is auto-generated from an approved proposal — it's a fully separate manual record with **no create-agreement UI at all** (the API action exists; nothing in `PartnerActionsPanel` or the detail page calls it, so today it's reachable only by direct API/Hermes call, not by a person using the app). No "Log Meeting" or "Send follow-up" quick-action buttons exist — the closest real equivalent is the generic note-adding form. The mockup's signed-agreement audit trail (James Parker signed / Alex K. approved, with dates) is **mockup-only, not implemented.** |

## Part 2 — Canonical-record architecture (secondary mockup)

The secondary mockup's core claim is: **one Person, one Partner** — every inquiry, booking, proposal, agreement, communication, and event links back to those two shared records, with full cross-linked history.

| Mockup concept | Real implementation | Verdict |
|---|---|---|
| Canonical **Partner** record, single source of truth, linked proposals/agreements/events | Real and correctly designed this way. `partners.ts`'s own doc comment states the principle explicitly: "The Partner lives ONCE, canonically... Business Worlds... consume references/projections of it — they never create a second record." `Proposal.partnerId` and `PartnerAgreement.relatedProposalId` implement the linkage. | **Matches** the architectural *principle*, for Partner specifically. |
| Canonical **Person** record, shared across Guests/Leads/VIP/Repeat, linked to Bookings, Inquiries, Communications, Experiences — independent of and prior to any Partner relationship | **Does not exist.** There is no `Person`/people-directory model anywhere in `sanctuary-nexus`. `PartnerContact` is the only person-shaped data, and it is a **nested array field on Partner** — a contact has no identity, profile page, or ID outside its parent Partner. It cannot represent a guest, lead, or repeat customer who isn't tied to a partner organization. | **Mockup-only, not implemented.** This is the single largest gap between the mockup and reality — the mockup's entire "People, Partners & Inquiries" concept assumes a Person model that Living OS never built. |
| Person ↔ Booking ↔ Product/Instance ↔ Operation chain (mockup's "People/Guest Workflow") | This chain is real, but it lives entirely in **this repo** (`bcc-website`), in Supabase (`bookings`, `event_dates`, `products`), not in Living OS. The two systems are completely unconnected today — no shared identifier, no API bridge, no sync. | **Differs / not bridged.** Both halves exist independently; the mockup implies they're one system, and today they are two systems with zero integration. |
| **Agreement → Event/Collaboration** activation step (mockup's "Partner/Organization Workflow" step 4: an agreement produces a real scheduled event) | Not implemented. `PartnerAgreement` has no field referencing an `event_dates`/`products` row (nor could it — those live in the other codebase's Supabase project). Turning a signed agreement into an actual bookable BCC/BNT product instance is entirely manual today, via the unrelated `/dashboard/products/new` flow this repo already flags as its own separate gap. | **Mockup-only, not implemented** — and structurally can't be, without deciding how (or whether) Living OS and the BCC-website Supabase schema should share identifiers. |
| **Communications Timeline** — unified email/WhatsApp/notes/system feed per person/partner | Partner has `notes[]` (manual relationship notes only — author, summary, decisions, next steps). No email or WhatsApp integration, no unified multi-channel log, no "system" event stream (e.g., no automatic entry when a proposal is approved or a PDF generated). | **Mockup-only, not implemented.** |
| Entity resolution to keep one canonical record instead of duplicates | `resolvePartner()` genuinely implements this for Partners (exact/alias/substring match, ambiguity flagged). No equivalent exists for Person, because Person doesn't exist. | **Matches** for Partner; **N/A / not implemented** for Person. |

## Part 3 — Cross-cutting gaps that apply to both mockups

These aren't mockup-comparison items so much as structural facts that bound what "migrating this to SNX Operator" would actually mean, carried forward and reconfirmed from `OX_OPERATOR_REUSE_AUDIT.md`:

- **Storage is a local JSON file**, not a database. `.sanctuary/runtime/work-data.json` via `readRuntimeWorkData`/`updateRuntimeWorkData`. Nothing here is durable across deployments or safe for concurrent/serverless use. Any migration requires a real backing store — this is not a data-shape problem, it's an infrastructure decision (already flagged in the handoff's Phase 4 builder plan and Phase 1 alignment audit §7a).
- **No production auth/identity.** The local-owner-session model explicitly refuses to run outside `NODE_ENV !== "production"` on loopback hosts. There is no concept of "James Parker" or "Alex K." as distinct authenticated actors anywhere in the code — the mockup's named-approver audit trail (step 6, step 8) has no identity system to attribute actions to even conceptually, let alone in a stored record.
- **No connection to `/operator` in this repo at all.** `sanctuary-nexus` is a fully separate, undeployed Next.js app. Nothing in `bcc-website`'s `/operator/create` "Coming next" card for Partner+Proposal currently calls any of this code — it's inert, per the handoff.
- **Proposal PDFs are not stored durably.** Every download regenerates the PDF on request from the frozen `approvedContent`; there is no archive of previously-sent PDFs as binary artifacts.

## Summary verdict

| Category | What it covers |
|---|---|
| **Matches** | Canonical single Partner record + entity resolution; Partner→Proposal linkage by `partnerId`; deal-variable carry-forward; AI draft generation with deterministic fallback; version-freeze-on-approve mechanics with 409 protection against editing frozen versions; gated, metadata-stripped PDF export from approved content only. |
| **Partially supports** | Proposal "setup" (real structured writing standard, but whole-document editing, not per-section); PDF/export step (real generation, but no send-tracking or durable storage). |
| **Differs from mockup** | Review step (no comments/annotations/named reviewers — just status + a single free-text revision instruction); approval audit trail (single timestamp, no per-actor log — because there's no auth to attribute to); Agreement step (metadata record only, no signature capture, no UI to even create one today). |
| **Mockup-only, not implemented** | Canonical Person/People-directory model entirely; communications timeline across channels; Agreement → live Event/Collaboration activation; any bridge between Living OS partner/proposal data and this repo's actual Supabase booking/event data. |

## What this means for scoping Phase 3A

The `SNX_OPERATOR_SESSION_HANDOFF.md`'s "Next recommended module" already flagged Partner+Proposal as the bigger, riskier of the two remaining options, contingent on "explicit sign-off on the schema question it raises." This audit sharpens that: the real gap isn't the Partner/Proposal engine itself (that part is genuinely solid — canonical record, entity resolution, versioning, approval-freeze, real PDF export) — it's that **the mockups describe a unified People+Partner CRM bridging Living OS and the live booking system, and neither the Person model nor the Living OS↔Supabase bridge exists anywhere today.** Any Phase 3A implementation plan needs to explicitly scope down to what's real (Partner + Proposal, migrated off local JSON onto a durable store) versus what would be new architecture (Person model, communications timeline, agreement e-signature, event activation) — not assume the mockups are describing a system that's mostly built and waiting to be wired in.

No recommendation is made here on whether/how to proceed — per the handoff, that decision point is explicitly deferred pending sign-off.
